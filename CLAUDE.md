## Overview

This repository contains infrastructure-as-code for a self-hosted observability stack using Dokploy. The stack includes:

- **GlitchTip** - Sentry-compatible error monitoring (web UI, Celery worker, PostgreSQL, Redis)
- **Metabase** - Business intelligence and analytics platform (with PostgreSQL backend)

All services are deployed via Docker Compose and orchestrated through Dokploy with Traefik for reverse proxy and SSL.

## Common Commands

### Setup and Development

```bash
# Generate secrets and create .env files from templates
make setup

# Generate secrets without writing to files (for manual copying)
make secrets

# Validate all docker-compose files
make validate

# Remove generated .env files
make clean
```

### Local Development

```bash
# Run GlitchTip locally (http://localhost:8000)
make local-glitchtip

# Run Metabase locally (http://localhost:3000)
make local-metabase

# Stop all local services
make local-down
```

Local development uses override files (`docker-compose.local.yml`) that disable Traefik labels and expose ports directly.

### Backups (VPS Only)

```bash
# Backup GlitchTip PostgreSQL database
make backup-glitchtip

# Backup Metabase PostgreSQL database
make backup-metabase

# Backup all databases
make backup-all
```

Backups are timestamped and saved to `./backups/` directory as gzipped SQL dumps.

## Architecture

### Network Architecture

The infrastructure uses a dual-network design:

1. **dokploy-network** (external): Shared network for Traefik routing. The web-facing service containers connect here.
2. **internal** (bridge): Isolated network per stack where all services communicate. Database and cache containers live only on this network.

This design ensures:
- Only web services are exposed to Traefik
- Databases remain isolated and unexposed
- Each stack (GlitchTip, Metabase) has its own internal network

### Service Communication

- **Traefik** (managed by Dokploy) routes HTTPS traffic to web services based on domain labels
- Services within a stack communicate via container names on the internal network
- SSL certificates are automatically managed by Let's Encrypt via Traefik

### Resource Management

All services have memory limits and reservations defined to prevent OOM conditions:

- **GlitchTip web**: 256M-1G
- **GlitchTip worker**: 256M-1G
- **GlitchTip PostgreSQL**: 128M-512M
- **GlitchTip Redis**: 64M-192M (with LRU eviction policy)
- **Metabase**: 512M-1.5G (Java heap: 512M-1G)
- **Metabase PostgreSQL**: 64M-256M

### GlitchTip Stack

- **web** service: Django application serving the UI and API
- **worker** service: Celery worker with beat scheduler for async tasks (email notifications, cleanup jobs)
- Both web and worker share the same image but run different commands
- **postgres** service: Dedicated PostgreSQL 16 database
- **redis** service: Task queue and caching

### Metabase Stack

- **metabase** service: Java-based analytics application
- **postgres** service: Dedicated PostgreSQL 16 for Metabase application data
- Plugin directory persisted in a volume

### Configuration Management

Environment variables are managed via:
1. `.env.example` files (templates with placeholders)
2. `.env` files (generated by `make setup` or `scripts/generate-secrets.sh --write`)
3. Dokploy UI environment variables (for production deployments)

Secret generation uses:
- `openssl rand -hex 32` for secret keys
- `openssl rand -base64 24` for passwords

### Deployment Strategy

1. **Local development**: Use `make local-*` commands which apply override files to disable Traefik and expose ports
2. **Production (Dokploy)**: Paste `docker-compose.yml` contents into Dokploy UI, set environment variables, configure domains with SSL

### Scripts

- **scripts/generate-secrets.sh**: Generates cryptographically secure secrets for all services. Works on both macOS (BSD sed) and Linux (GNU sed).
- **scripts/init-vps.sh**: VPS initialization script (installs Dokploy and configures system)

## Important Notes

### Docker Compose Validation

Always validate compose files after changes:
```bash
make validate
# Or manually:
cd observability/glitchtip && docker compose config --quiet
cd observability/metabase && docker compose config --quiet
```

### Traefik Labels

The Traefik labels follow this pattern:
- `traefik.enable=true` - Enable routing for this service
- `traefik.http.routers.<name>.rule=Host(...)` - Domain routing rule
- `traefik.http.routers.<name>.entrypoints=websecure` - Use HTTPS entry point
- `traefik.http.routers.<name>.tls.certresolver=letsencrypt` - Enable SSL
- `traefik.http.services.<name>.loadbalancer.server.port=<port>` - Internal port
- `traefik.docker.network=dokploy-network` - Network for Traefik to watch

### Database Container Names

Backup commands in the Makefile use pattern matching to find containers:
- `docker ps -qf "name=glitchtip.*postgres"` for GlitchTip
- `docker ps -qf "name=metabase.*postgres"` for Metabase

This works with Dokploy's container naming conventions.

### Environment Variables

Required environment variables:

**GlitchTip:**
- `SECRET_KEY` - Django secret key (hex 64 chars)
- `DB_PASSWORD` - PostgreSQL password
- `GLITCHTIP_DOMAIN` - Domain without https:// prefix (e.g., `errors.example.com`)
- `EMAIL_URL` - Optional SMTP URL (defaults to `console://`)
- `DEFAULT_FROM_EMAIL` - Optional sender email

**Metabase:**
- `MB_DB_PASSWORD` - PostgreSQL password
- `METABASE_DOMAIN` - Domain without https:// prefix (e.g., `analytics.example.com`)
- `MB_SITE_NAME` - Optional site name (defaults to "Analytics")

### Health Checks

PostgreSQL containers have health checks that other services depend on:
```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U <user> -d <database>"]
  interval: 10s
  timeout: 5s
  retries: 5
```

This ensures web services don't start until the database is ready.
